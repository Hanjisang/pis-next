# PIS Next 出站接口与业务对账核心场景

文档状态：草稿  
文档版本：0.1  
创建日期：2026-08-05

## 1. 文档目的

本文详细定义 PIS Next 第一版中病理业务状态回传、正式病理报告回传和接口业务对账的核心业务场景。

本文重点说明：

- 本地病理业务事实与出站消息之间的区别；
- 业务事件与当前状态展示之间的区别；
- 消息发送结果、技术应答和外部业务处理结果之间的区别；
- 重复发送和业务幂等；
- 状态回传的对象范围和业务语义；
- 报告、报告版本和报告 PDF 之间的区别；
- 正式报告版本、补充版本、更正版本和撤回通知的回传；
- 本地报告生命周期与外部系统展示状态之间的边界；
- 接口发送记录和每次发送尝试之间的区别；
- 漏发、重复、乱序、错发和版本不一致的业务对账；
- 对账差异与本地业务事实之间的边界；
- 正常业务变化；
- 待业务确认问题；
- 后续领域模型、接口流程、状态机和测试设计输入。

本文不定义：

- 具体接口协议；
- 具体请求和响应报文；
- 数据库结构；
- API 字段；
- 页面操作；
- 消息中间件实现；
- 具体重试和调度参数；
- 完整补偿操作矩阵。

本阶段继续坚持以下边界：

- 本地业务事实不等于回传消息；
- 消息发送成功不等于外部业务处理成功；
- 外部技术应答不等于外部业务已经生效；
- 报告回传不等于修改报告生命周期；
- 接口对账不等于自动篡改本地业务事实。

## 2. 术语和参与者使用说明

本文统一使用术语表中的“病理申请”“病理病例”“标本”“技术医嘱”“报告”“报告版本”“报告签发”“补充报告”“报告更正”“报告撤回”“报告重新签发”“报告 PDF”“外部标识”“幂等”“对账”“审计事件”等术语。

本文使用“接口消息”表达接口业务中的出站消息事实；如果后续术语评审认为该表达不是正式术语，应在术语评审中单独确认，不在本任务中修改术语表。本文使用“发送尝试”表达一次实际发送行为的独立追溯记录，不把发送尝试等同于业务事件或本地病理业务操作。

本文引用系统上下文中已经识别的 HIS、EMR、医院统一集成平台、临床申请系统、报告调阅系统或临床门户。具体医院使用哪些系统、哪个系统是某类回传的目标、目标系统如何确认外部业务生效，均为待业务确认问题，不在本文中固定。

本文引用角色文档中的接口运维人员、病理登记人员、标本接收人员、病理技术人员、初诊医生、报告签发医生、质量管理人员、病理科管理人员和审计人员。接口运维人员可以处理重试、人工重放和对账，但不得直接修改核心业务事实或正式报告内容。

## SCN-PIS-093：回传病理业务状态

场景编号：SCN-PIS-093

场景名称：回传病理业务状态

场景状态：草稿

主要分类：SC-CAT-11 医院接口

业务目标：

PIS 根据已经发生并提交成功的病理业务事实，向授权外部医院系统回传可理解的业务进展信息，同时保留本地业务事实、出站消息、发送尝试和外部处理结果之间的边界。

主要参与者：

- HIS；
- EMR；
- 医院统一集成平台；
- 临床申请系统。

以上参与者均为系统上下文中已经识别的外部系统。实际回传目标、目标优先级和目标系统可接收的业务范围待业务确认。

协作参与者：

- 接口运维人员；
- 病理登记人员；
- 标本接收人员；
- 病理技术人员；
- 初诊医生；
- 报告签发医生；
- 审计人员。

触发事件：

- 病理申请被 PIS 接收；
- 病理病例建立；
- 标本实际接收；
- 取材或技术处理达到可回传节点；
- 技术医嘱处理进展发生变化；
- 病例进入诊断或报告环节；
- 正式报告已经签发；
- 报告被补充、更正或撤回；
- 术中冰冻轮次形成结果；
- 需要重新发送此前未成功回传的业务进展。

不得把定时任务执行作为唯一业务触发事件。

前置条件：

1. 本地业务对象身份明确；
2. 本地业务事实已经成功形成；
3. 目标外部系统可以识别；
4. 外部业务标识可以识别；
5. 回传所依据的业务事件或业务节点可以识别；
6. 回传目标对象与当前病例关系正确；
7. 当前业务信息满足目标系统所需的最低语义要求；
8. 当前回传不会引用未提交或已经回滚的本地业务事实；
9. 接口配置允许向该目标系统回传相应业务信息。

涉及对象：

- 病理申请；
- 病理病例；
- 标本容器；
- 标本；
- 技术医嘱；
- 报告版本；
- 术中冰冻；
- 冰冻送检批次；
- 外部标识；
- 接口消息；
- 幂等；
- 审计事件。

如术语表没有正式定义“接口消息”，本文仅将其作为接口业务表达，不新增正式术语。

成功结果：

1. 已基于明确本地业务事实形成回传业务内容；
2. 回传目标外部系统明确；
3. 回传对象及其外部标识明确；
4. 回传所依据的业务事件或节点可以追溯；
5. 出站消息具有可追溯身份；
6. 同一业务事实重复触发时不会形成冲突的外部业务结果；
7. 每次实际发送尝试可以分别追溯；
8. 消息形成时间和发送时间可以区分；
9. 发送结果可以记录；
10. 技术应答结果可以记录；
11. 外部业务处理结果如可获得，可以单独记录；
12. 回传失败不会改变本地病理业务事实；
13. 重新发送不会修改原业务事件；
14. 乱序风险可以被识别；
15. 接口回传行为形成审计记录。

业务约束：

1. 本地病理业务事实是回传依据；
2. 出站消息不等于本地业务事实；
3. 当前状态展示不等于完整业务事件历史；
4. 病例整体状态不得覆盖标本、医嘱、报告或冰冻轮次的真实结果；
5. 不得回传尚未成功提交的业务事实；
6. 消息形成成功不等于消息发送成功；
7. 消息发送成功不等于收到技术应答；
8. 技术应答成功不等于外部业务已经生效；
9. 外部业务已经生效不等于临床用户已经查看；
10. 回传失败不得回滚标本接收、技术执行、报告签发等本地事实；
11. 接口重试不得形成新的病理业务事实；
12. 每次重试必须保留独立发送尝试；
13. 重试不得覆盖此前失败记录；
14. 同一业务事件重复回传必须满足幂等要求；
15. 幂等标识不得仅依赖不可控显示文本；
16. 同一对象不同业务事件不得被误判为重复；
17. 状态回传必须明确对应的业务对象；
18. 不得仅回传一个病例级状态而丢失必要对象范围；
19. 旧业务进展晚于新进展送达时不得使外部系统无条件回退；
20. PIS 应能够识别潜在乱序，但本阶段不定义具体算法；
21. 不同外部系统可以使用不同状态表达，但不得改变本地业务语义；
22. 外部系统状态编码变化不得改变历史回传含义；
23. 外部处理失败不得无条件改写本地业务状态；
24. 外部系统返回的状态不得被当成本地事实来源；
25. 消息被取消发送不得删除原业务事件；
26. 人工补发必须保留操作人员和原因；
27. 不得通过修改原发送记录表示再次发送；
28. 接口停机期间本地病理业务应能继续；
29. 接口恢复后补传必须避免重复和乱序；
30. 状态回传中的患者敏感信息应遵循最小必要原则；
31. 状态回传记录不得被普通业务人员无痕修改；
32. 无法自动确认外部处理结果时，应保留待对账事实。

主要业务变化：

- 病理申请接收回传；
- 病理病例建立回传；
- 标本接收回传；
- 取材完成回传；
- 技术处理中回传；
- 技术医嘱部分完成回传；
- 初诊或审核进展回传；
- 报告签发回传；
- 报告更正或撤回相关状态回传；
- 冰冻第一轮接收回传；
- 冰冻多轮分别回传；
- 同一业务事件回传多个外部系统；
- 一个外部系统成功、另一个失败；
- 接口停机后批量补传；
- 重复触发同一状态回传；
- 旧状态晚于新状态发送；
- 发送成功但无应答；
- 技术应答成功但外部查询不到；
- 人工补发；
- 外部系统状态编码发生变化。

待确认问题：

1. 第一版需要回传哪些业务节点；
2. 状态回传按病例还是按具体对象；
3. 标本接收是否按容器、标本或病例回传；
4. 技术医嘱是否按医嘱或项目回传；
5. 冰冻是否按业务或送检轮次回传；
6. 报告签发是否同时回传状态和报告；
7. 补充、更正和撤回需要哪些状态通知；
8. 哪些外部系统需要状态回传；
9. 不同系统是否使用不同状态映射；
10. 状态映射由谁维护；
11. 状态编码变化如何管理；
12. 业务事件唯一识别依据；
13. 重复回传如何实现业务幂等；
14. 是否需要业务顺序号或版本信息；
15. 外部系统是否支持拒绝旧状态；
16. 消息发送成功的判断标准；
17. 技术应答成功的判断标准；
18. 外部业务生效如何确认；
19. 是否需要外部处理回执；
20. 是否需要临床查看确认；
21. 回传失败是否通知业务人员；
22. 哪些失败只通知接口运维人员；
23. 哪些业务允许人工补发；
24. 人工补发是否需要审批；
25. 补发是否允许修改原回传内容；
26. 接口停机恢复后补传范围如何确定；
27. 状态回传是否需要对账；
28. 外部系统无法表达部分完成时如何处理；
29. 外部状态回退是否允许；
30. 状态回传记录保存期限如何确定。

## SCN-PIS-094：回传正式病理报告

场景编号：SCN-PIS-094

场景名称：回传正式病理报告

场景状态：草稿

主要分类：SC-CAT-11 医院接口

业务目标：

PIS 将已经正式签发的具体病理报告版本及其必要内容受控回传至授权外部系统，保持报告对象、报告版本、报告 PDF 和外部处理结果之间的清晰边界，并支持补充、更正、撤回和重新签发后的版本通知。

主要参与者：

- HIS；
- EMR；
- 报告调阅系统；
- 临床门户；
- 医院统一集成平台。

以上参与者均为系统上下文中已经识别的外部系统或外部系统类型。具体目标系统和接收能力待业务确认。

协作参与者：

- 报告签发医生；
- 接口运维人员；
- 病理登记人员；
- 质量管理人员；
- 审计人员。

接口运维人员不得修改正式报告内容。

触发事件：

- 正式病理报告版本签发成功；
- 补充报告版本签发成功；
- 更正报告版本签发成功；
- 报告被撤回；
- 报告撤回后形成重新签发版本；
- 此前正式报告回传失败，需要重新发送；
- 对账发现报告漏发或版本不一致。

前置条件：

1. 报告对象身份明确；
2. 目标报告版本身份明确；
3. 目标版本已经正式签发；
4. 报告版本关联正确病理病例；
5. 报告版本类型可以识别；
6. 当前有效版本关系可以识别；
7. 报告内容完整；
8. 报告 PDF 如需要回传，必须绑定目标报告版本；
9. PDF 内容与目标报告版本一致；
10. 外部目标系统和外部业务标识可以识别；
11. 接口配置允许向目标系统回传；
12. 当前回传不会发送报告草稿；
13. 当前操作人员和系统行为可以审计。

涉及对象：

- 病理病例；
- 报告；
- 报告版本；
- 报告签发；
- 补充报告；
- 报告更正；
- 报告撤回；
- 报告重新签发；
- 报告 PDF；
- 外部标识；
- 幂等；
- 审计事件。

成功结果：

1. 已选定明确正式报告版本进行回传；
2. 回传目标病例和外部业务标识正确；
3. 回传目标外部系统明确；
4. 回传版本类型可以识别；
5. 回传内容与该报告版本一致；
6. 回传的 PDF 如存在，绑定该具体版本；
7. 原历史版本不会因回传新版本被删除；
8. 每次报告回传形成可追溯出站记录；
9. 每次实际发送尝试可以分别追溯；
10. 重复发送同一版本不会产生冲突业务结果；
11. 补充、更正和重新签发版本可以分别识别；
12. 撤回通知和报告版本回传可以区分；
13. 发送结果可以记录；
14. 技术应答可以记录；
15. 外部业务应用结果如可获得，可以单独记录；
16. 回传失败不会改变本地报告签发事实；
17. 外部系统不支持版本时，本地完整版本链仍保持不变；
18. 报告回传行为形成审计记录。

业务约束：

1. 只有正式签发报告版本可以正常对外回传；
2. 报告草稿不得作为正式报告回传；
3. 审核通过但未签发的内容不得回传；
4. 报告对象不等于报告版本；
5. 报告版本不等于报告 PDF；
6. PDF 文件不等于报告签发事实；
7. 每次回传必须指向明确报告版本；
8. 不得只回传病例级“最新报告文本”而丢失版本身份；
9. 本地报告签发成功不等于报告回传成功；
10. 报告回传失败不等于本地签发失败；
11. 外部接收成功不等于临床用户已经查看；
12. 报告回传不得修改本地报告版本；
13. 报告回传不得改变版本签发人和签发时间；
14. 报告回传重试不得形成新报告版本；
15. 每次重试必须保留独立发送尝试；
16. 同一报告版本重复回传必须满足业务幂等；
17. 补充报告必须以新版本身份回传；
18. 更正报告必须以新版本身份回传；
19. 重新签发报告必须以新版本身份回传；
20. 撤回不得表现为删除本地报告；
21. 撤回通知必须指向明确被撤回版本；
22. 被撤回版本仍然保留；

## SCN-PIS-095：执行接口业务对账

场景编号：SCN-PIS-095

场景名称：执行接口业务对账

场景状态：草稿

主要分类：SC-CAT-11 医院接口

业务目标：

接口运维人员或授权系统根据 PIS 本地业务事实、出站发送记录、外部技术应答和可获得的外部业务结果，对患者申请、状态、收费和正式报告等接口业务进行核对，识别漏发、重复、乱序、错配和版本不一致，并形成受控处理依据。

- 接口运维人员。

- 病理技术人员；

- 病理科管理人员；

- HIS；
- EMR；
- 医院统一集成平台；
- 报告调阅系统或临床门户；
- 收费系统。

外部系统仅作为对账范围内的结果来源或核对对象，不因参与对账而获得修改 PIS 核心业务事实的权限。

触发事件：

- 定期开展接口业务核对；
- 接口故障恢复后需要核对积压业务；
- 业务人员发现外部系统数据缺失或错误；
- 报告签发后临床系统未显示；
- 状态回传结果与外部系统展示不一致；
- 收费或退费结果无法关联；
- 外部系统返回失败或不确定结果；
- 系统发现重复、乱序或版本冲突；

2. 对账时间范围可以明确；

3. 相关接口消息和发送尝试可以识别；
4. 外部技术应答可以识别；
