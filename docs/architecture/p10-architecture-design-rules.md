# P10 全病理系统架构设计规则

文档状态：P10架构设计中
适用阶段：P10-ALL-MODALITY-SYSTEM-ARCHITECTURE-FINAL
上游基线：P09需求基线、P08状态机、P07异常矩阵、P06业务流程、P05领域模型

## 1. 架构边界

### P10-RULE-001：架构必须由已确认基线驱动

每项架构决策必须能够追溯到正式需求、验收准则、患者安全风险、领域聚合、不变量、流程、异常、状态机或确认决策。个人技术偏好不能成为无来源的架构依据。

### P10-RULE-002：架构层次必须分开

P10分别描述逻辑业务模块、组件责任、运行组件、外部适配器和未来部署单元。模块不是服务，组件不是部署地址，架构编号不是代码、接口或持久化对象名称。

### P10-RULE-003：架构风格必须比较后决定

必须比较模块化单体、少量独立组件和全面服务化方案，依据独立伸缩、独立交付、独立安全域和故障隔离证据作出选择。规模本身不能推出全面服务化。

### P10-RULE-004：聚合必须有唯一主归属

18个正式聚合各自具有一个主责任模块。其他模块不得直接改变归属模块拥有的业务事实，只能通过公开应用能力、受控查询、业务事件或协调流程协作。

### P10-RULE-005：模块之间不得共享可写事实

跨模块共享查询不等于共享写入。任何模块不得直接修改其他模块的内部领域事实，循环写依赖必须为零。

### P10-RULE-006：本地强一致优先

聚合内身份、来源、责任、版本、状态守卫、质控释放和报告签发等核心不变量在本地一致性边界内完成。P10不定义具体持久化结构、锁语句或隔离级别。

### P10-RULE-007：最终一致必须可观察

跨模块或外部协作必须说明发起事实、可靠事件、消费幂等、处理状态、失败、重试、补偿、对账、人工介入和完成条件。

### P10-RULE-008：业务事实与投递状态分离

本地报告签发、材料形成、结果确认、纠错批准和销毁完成等事实不因投递、回执或外部业务状态失败而回滚。

### P10-RULE-009：历史保护优先

报告版本、材料身份、诊断依据、原始结果、质控结果、审计事件、外部原始消息和恢复证据保持不可变或追加关系。修订必须形成新事实、版本、作废、撤回或受控纠错记录。

### P10-RULE-010：状态机归属明确

31个状态机由拥有对象的模块负责。任务编排只能辅助待办、提醒、超时和人工协调，不能替代正式领域状态或成为唯一事实来源。

### P10-RULE-011：全病理共性与类型路径分离

申请、病例、患者和就诊上下文、标本身份、责任、审计、报告生命周期、接口、质量和归档是共享能力。组织、冰冻、细胞、分子、外送和多模态的材料、检测、筛查和判读路径保持独立。

### P10-RULE-012：文件和业务元数据分离

报告PDF、数字切片、外部报告和其他文件的业务元数据、文件身份、版本、存储定位、完整性、可用性、引用和生命周期分开表达。二进制文件不是唯一业务事实。

### P10-RULE-013：外部系统必须经过防腐层

HIS、EMR、LIS、设备、扫描系统、外送机构和其他外部能力通过适配器、身份映射、编码映射、状态映射、版本控制、原始消息保存和对账接入，不能污染核心领域术语和状态。

### P10-RULE-014：身份认证与业务授权分离

身份认证、组织上下文、角色授权、对象范围、数据范围、任务责任、代理、临时授权、强认证和第二人复核是不同架构能力。P10不冻结P14详细权限矩阵。

### P10-RULE-015：人工身份与服务身份分离

人工用户、设备、接口和后台任务使用可区分身份类型。服务身份不能成为医学诊断、报告签发或高风险纠错的人工责任人。

### P10-RULE-016：审计、异常和质量事件分离

审计证明谁在何时执行了什么操作；异常表达影响和处置；质量事件表达调查、影响和关闭；三者不能合并为万能日志。

### P10-RULE-017：局部故障隔离

单个标本、蜡块、玻片、检测任务、扫描任务、文件生成、外部系统或投递目标失败，只影响其关联路径。无关联依据时不得阻断全部病例。

### P10-RULE-018：未确认参数不得赋值

P09-PARAM-001至P09-PARAM-018全部保留未确认状态。架构只提供测量点、配置边界、调整能力、责任和确认入口，不填写具体时限、比例、数量、RPO或RTO。

### P10-RULE-019：模块数量由责任形成

逻辑模块数量由聚合、对象、流程、状态机、异常和质量属性共同决定，不以预设数量凑数。模块可以合理合并，但必须记录被合并责任和边界理由。

### P10-RULE-020：事件数量由协作形成

不为每个状态转换机械创建事件。只有跨模块责任交接、外部集成、可靠投递、对账或必须独立观察的业务事实才进入架构事件目录。

### P10-RULE-021：事务边界必须可解释

每项事务场景必须标记主模块、涉及聚合、即时不变量、可最终一致结果、重复请求、并发冲突、失败分类、补偿、对账和审计方式。

### P10-RULE-022：架构编号稳定

模块使用P10-MOD-001，组件使用P10-CMP-001，架构能力使用P10-CAP-001，事务场景使用P10-TXN-001，架构事件使用P10-EVT-001，架构风险使用P10-ARISK-001。编号只用于架构追溯，不提前作为实现名称。

### P10-RULE-023：配置不得覆盖安全底线

医院可以配置编号规则、显示、提醒、非核心阈值、设备能力、报告模板、外部机构和流程启用范围，不能关闭身份稳定、来源链、责任识别、版本保护、患者安全阻断和审计证据保护。

### P10-RULE-024：架构必须可进入后续阶段

P10向P11提供数据归属和关系边界，向P12提供应用能力和事件契约边界，向P14提供权限点，向P24提供工作站责任，向P25提供事务和异常验证入口，向P27提供运行能力和恢复目标入口。

## 2. 阶段排除

P10不创建数据库表、交换协议细节、接口字段契约、完整权限矩阵、页面和控件设计、测试用例、代码、部署拓扑或服务器规格。上述内容只作为后续阶段输入。

P10的最终选择为逻辑架构和责任边界，不宣称已完成实现、性能验证、安全认证、接口联调或生产恢复演练。
