# P10 全病理事务与一致性架构

文档状态：P10架构设计中
事务场景总数：15
分类：聚合内强一致8；同模块多聚合协调3；跨模块最终一致2；外部系统最终一致2

## 1. 总体一致性选择

P10采用“聚合内本地强一致、同模块多聚合受控协调、跨模块可靠事件最终一致、外部系统对账最终一致”。外部系统不参与本地事务提交；本地事实先形成，之后记录出站事件、投递、外部技术应答、外部业务确认和对账差异。

## 3. 一致性机制

### 3.1 聚合内强一致

以下业务事实必须在主责任模块的本地事务边界内完成：

- 对象身份、来源、责任和版本的形成；
- 状态转换守卫及禁止转换；
- 业务编号正式生效；
- 材料消耗和剩余量事实；
- 分子质控与有效性确认；
- 授权关系生效；
- 报告签发和报告版本事件；
- 销毁执行结果和恢复校验结果。

事务成功意味着主聚合事实和必要审计事实已形成；文件生成、通知和外部回传不属于该本地提交的前提。

### 3.2 同模块多聚合协调

同一模块内多个聚合协作时，协调记录必须表达已完成、待完成、失败、补偿和人工关闭，不把协调状态写成被协调聚合的新状态。每个聚合的主责任模块保持独立写入权。

### 3.3 跨模块协作

跨模块协作使用不可变业务事件或受控应用命令。消费方必须以事件身份、来源版本和目标对象建立幂等判断；消费失败不删除发起方事实，必要时形成受阻任务、补偿请求和对账差异。

### 3.4 外部协作

外部协作顺序固定为：

```text
本地业务事实
→ 出站业务事件
→ 单次投递尝试
→ 外部技术应答
→ 外部业务确认
→ 对账
→ 补偿或人工关闭
```

外部技术应答不等同于外部业务生效；外部业务生效不覆盖本地报告、材料、结果或责任事实。

## 4. 幂等和重复处理

| 重复类型 | 识别依据 | 处理结果 |
|---|---|---|
| 入站申请重复 | 来源、外部申请标识、原始消息标识 | 返回原接收事实或进入归并审查 |
| 业务命令重复 | 命令来源、业务对象、操作意图和请求关联 | 不重复形成业务事实 |
| 事件消费重复 | 事件身份、版本、消费者责任和处理记录 | 返回既有消费结果 |
| 文件重传 | 文件来源、业务引用、版本和完整性 | 不静默替换已引用版本 |
| 外部回执重复 | 目标、外部标识、事件版本和回执版本 | 追加投递/对账事实，不重复改变本地业务状态 |
| 人工重放 | 原事件、授权人、重放原因和新尝试身份 | 新投递尝试，不新建申请、报告或材料事实 |

## 5. 并发冲突

并发冲突按业务事实分类：

- 身份或来源冲突：阻断高风险动作，保留双方证据并转授权复核；
- 同一材料消耗冲突：只有一个消耗事实成功，其余进入待处理；
- 同一报告版本提交冲突：先形成的版本保留，后续内容形成新版本或被拒绝；
- 同一状态转换冲突：按状态机守卫拒绝过期转换；
- 同一外部回执冲突：保留原始回执并建立对账差异；
- 同一授权冲突：撤销或过期优先于未完成动作。

P10只定义业务并发规则，不定义具体存储锁、隔离级别或实现语句。

## 6. 异常、补偿和完成条件

每个事务场景必须有可观察的成功、失败、受阻、补偿和关闭事实。补偿不是删除原事实，而是创建新责任、新尝试、新版本或受控关闭记录。局部异常只影响关联对象；SEV-1异常可阻断其安全范围内的下游路径，但不得扩大到无关联业务。
