# P14 全病理授权安全设计规则

文档状态：P14 已设计

阶段名称：P14 用户权限与审计

任务：P14-ALL-MODALITY-AUTHORIZATION-SECURITY-FINAL

## 1. 目的与边界

本文件把 P10 的安全治理边界、P11 的数据保护要求和 P12 的契约守卫细化为可追溯的授权设计规则。P14 只定义主体、授权、数据范围、任务责任、代理、高风险控制、职责分离和审计证据，不选择身份平台，不定义认证协议，不创建数据库表，不实现后端授权代码，也不创建前端工作站。

授权的最小判断单位是“主体在一个明确上下文中对一个对象执行一个动作”。菜单、页面、工作站和调用通道只能提供交互或路由，不构成安全边界。

## 2. 正式设计规则

### P14-RULE-001：认证与授权分离

认证只证明主体及认证强度；授权另行判断主体是否有资格、范围、责任和当前状态下执行动作。认证成功不得直接产生业务允许结论。

### P14-RULE-002：默认拒绝与故障安全

授权输入缺失、来源不可信、版本冲突、状态不允许、策略不可判定或授权服务异常时，结果只能是拒绝、隔离、待复核或人工裁决；不得因异常而放行。

### P14-RULE-003：主体类型明确

人工主体、服务身份、后台任务身份、设备身份和外部系统身份必须可区分。主体类型、主体标识、认证上下文、组织上下文和有效期必须进入授权决策证据。

### P14-RULE-004：角色不是唯一依据

角色只提供候选业务能力。最终授权必须同时考虑能力、权限、组织范围、数据范围、病理类型、对象状态、任务责任、资格、代理、临时/紧急上下文和高风险要求。

### P14-RULE-005：能力与权限语义稳定

能力描述业务意图，权限描述一个可审计的动作入口；两者均不得退化为任意表、任意字段或任意对象的通用写入。每个正式权限必须有对象、动作、前置状态、责任和审计结论。

### P14-RULE-006：交互层不构成边界

交互界面、工作站和路由隐藏只能改善使用体验。真正的授权必须在业务命令、查询、文件引用、事件重放和治理动作的业务边界重新判断。

### P14-RULE-007：最小组织与数据范围

主体只能访问完成当前职责所需的最小医院、院区、科室、工作组、队列、病例、对象、时间和敏感度范围。范围扩大必须有独立理由、批准和审计。

### P14-RULE-008：任务责任守卫

任务的分配人、接管人、实际操作者、被代理责任人、批准人和复核人分别记录。需要承担业务责任的动作必须存在有效责任任务或明确的责任转移事实。

### P14-RULE-009：对象状态守卫

授权不能绕过 P08 状态机。动作必须匹配对象当前状态、上游事实、版本和跨对象守卫；禁止用通用状态修改语义替代业务动作。

### P14-RULE-010：患者安全规则不可关闭

身份、来源、材料链、诊断依据、报告版本、隔离、冻结、销毁、恢复和关键质量守卫不得被医院配置、角色配置、代理、紧急授权或运维操作关闭或改写。

### P14-RULE-011：实际操作者与业务责任分离

实际操作者是发起动作的主体；业务责任人对业务事实负责；代理人、批准人和独立复核人是不同的关系。代理不会把实际操作者改写成被代理人。

### P14-RULE-012：系统管理员不取得临床责任

系统管理员可以管理组织、主体映射、能力配置和技术治理，但不因系统管理职责自动获得取材、诊断、医学判读、报告签发或临床复核责任。

### P14-RULE-013：服务与设备身份受限

服务身份可以接收消息、提交原始事实、执行后台任务、生成文件和投递事件；设备身份可以回传执行事实、原始载荷和质量数据。二者均不能承担任何医学责任、临床批准或独立复核责任。

### P14-RULE-014：外部系统边界固定

外部系统只能通过 P12-HIF-001 至 P12-HIF-012 既定接口进入或接收事实。外部身份不能直接改变核心业务事实，也不能把外部结果伪装为本地执行事实。

### P14-RULE-015：代理必须显式建模

代理关系必须包含授权人、被代理人、代理类型、能力、对象/数据范围、起止时间、原因、批准人、撤销事实和使用审计。未形成有效关系不得以代理名义执行。

### P14-RULE-016：临时授权自动失效

临时授权必须有不可延后的失效时间和最小范围；到期、撤销、主体失效或责任任务结束后，所有新动作重新判断，不得依赖旧会话或缓存结论。

### P14-RULE-017：紧急授权可追责

紧急授权只能用于明确的患者安全或业务连续性风险，必须强认证、限定对象和时间、记录理由与影响，并在事后生成独立复核和关闭证据。紧急通道不能成为常规绕过路径。

### P14-RULE-018：高风险动作要求增强认证

身份/编号纠错、报告签发或受控版本事件、销毁、恢复开放、权限变更、接口重放和敏感导出等动作按 P14 高风险目录要求增强认证，必要时强制重新认证或人工确认。

### P14-RULE-019：独立第二人复核

患者安全、高风险纠错、报告受控版本、销毁、恢复和紧急授权等动作按风险要求由独立第二主体复核。复核人不能是同一动作的实际操作者，系统管理员也不能通过技术身份替代复核。

### P14-RULE-020：职责分离来自正式流程

职责分离只依据 P06/P08/P12 已定义的业务责任和 P02 角色原则形成，不能为了制造角色数量而任意拆分。医院规模不足时只能通过受控例外、批准和审计处理，不得静默合并关键责任。

### P14-RULE-021：授权结论可解释可审计

每次允许、拒绝、待强认证、待第二人复核、待批准、任务接管或人工裁决都必须记录决策输入摘要、命中的规则、范围、责任、版本、原因、审计引用和关联事件。敏感值只按最小必要性记录。

### P14-RULE-022：历史证据不可篡改

权限、角色、范围、代理和授权策略变更只能影响未来决策；既有业务事实、既有授权结论和审计历史不因配置变更而重写。P14 设计不把该规则下沉为数据库或实现细节。

## 3. 决策顺序

授权判断按以下顺序形成单一结论：主体存在与状态 → 认证强度 → 主体类型限制 → 角色与资格 → 组织和数据范围 → 任务责任 → 对象、病理类型和状态 → 代理/临时/紧急上下文 → 高风险与职责分离 → 并发版本 → 患者安全守卫 → 形成允许、拒绝或受控中间结论 → 写入审计证据。

任一前置项为否，停止后续放行判断并返回稳定的处理方向。查询、文件引用、事件重放、治理命令和外部接口均采用同一顺序。

## 4. 后续实现约束

后续阶段可以选择认证产品、协议、策略执行组件和持久化实现，但不得改变本文件的规则语义。实现验证必须覆盖授权单元测试、状态守卫、组织/数据范围、并发、高风险、代理、紧急通道、服务/设备边界和审计不可变性。
