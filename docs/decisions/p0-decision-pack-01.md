### 4.1 BD-P04-001：申请与病例形成关系及拆分合并边界

- 决策项编号：BD-P04-001
- 决策主题：申请与病例形成关系及拆分合并边界
- 原始决策引用：BD-P04-001（来源：P04 业务决策待确认台账）
- 主要场景：SCN-PIS-001、SCN-PIS-003
- 原始问题引用：Q-SCN-PIS-001-01、Q-SCN-PIS-003-01、Q-SCN-PIS-003-04
- 台账阻塞的后续工作：P05-001 核心领域对象识别
- 已确认事实：
  - 病理申请是业务请求，不等同于病理病例；接收外部申请不等于建立病例；一个申请可能形成一个或多个处理对象，具体规则尚待确认。
- 原待确认问题（已由本次确认结论覆盖）：
  - 一个外部病理申请与病理病例之间采用什么关系？何时允许拆分、合并或重新关联？
- 候选方案：
  - 候选 A：固定一申请一病例，任何拆分或合并均不允许。
    - 比较：规则简单，但无法表达同一申请对应多个独立处理对象或受控纠错。
  - 候选 B：申请和病例保持独立身份，允许在明确条件下形成一对多关系，并通过受控业务记录处理拆分/合并。
    - 比较：能保留请求事实和病例处理事实，但需要明确准入、责任和审计。
  - 候选 C：不建立独立病例身份，仅把病例视为申请的状态或视图。
    - 比较：与现有术语和全流程追溯要求冲突，无法承载独立病例号和后续对象链。
- 原推荐方向：建议作为确认起点采用候选 B 的方向：申请和病例独立识别，拆分/合并必须是显式、受控、可审计的业务事实，不允许静默覆盖或删除原关系。
- 建议理由：该方向同时保留外部请求原貌和 PIS 内部处理对象的独立追溯能力，并为多标本、多来源和异常处理留下明确边界。
- 如果不采用建议方向的主要风险：若不采用独立关系，可能出现病例重复、病例缺失、病理号无法稳定追溯，以及后续标本、蜡块、切片和报告挂接错误。
- 对 P05 的影响：P05-001 的核心对象识别、病例/申请关系和后续所有来源链设计将被直接阻塞。
- 业务确认结论：采用方案 B，并增加受控拆分、严格限制合并及全程留痕条件。
- 最终结论：病理申请与病理病例保持独立业务身份；默认一份申请对应一个病例；在明确、受控条件下允许一份申请形成多个病例；多份申请合并至一个病例原则上禁止，仅允许对经核实的重复申请建立受控关系；已形成独立业务事实的病例不得破坏性合并；申请与病例关系变更必须保留完整历史和审计记录。
- 确认状态：已确认。
- 确认人：未提供，待补录。
- 确认日期：2026-08-05（本次记录日期）。
- 已确认附加业务约束：
  - 申请拆分仅限独立处理、独立诊断、独立报告、不同病理业务类型、医院明确要求，或经授权确认原申请无法满足独立处理要求的场景。
  - 拆分必须记录原因、操作人员和时间，保留原申请及其与全部病例的关系；不得复制申请后切断来源，不得修改原病例伪造拆分，不得复用其他病例内部身份。
  - 多申请合并仅限经核实的重复申请、外部系统重复生成且尚未形成独立实际处理，且由授权人员确认保留一个病例继续处理的情况。
  - 重复申请处理必须保留全部原始申请，标识主申请和重复申请关系，记录判断依据、人员和时间；不得物理删除申请或因归并删除下游对象和报告历史。
  - 已分别形成独立病例、独立标本处理或独立报告生命周期的申请，不得破坏性合并；可通过相关病例或关联病例表达联系，但不得覆盖业务事实。
  - 关系错误允许通过受控纠错重新关联，必须记录原关系、目标关系、错误原因、操作人员、审核人员和时间，保留变更前后关系，并评估患者、标本、诊断和报告影响；必要时触发质量事件评估。
  - 随业务进展逐步收紧重新关联控制：病例建立但标本未接收时可授权纠正；标本接收后须核对实物和标签；完成取材、制片或诊断后须评估下游对象；报告草稿形成后须重新核对报告；正式报告签发后不得直接修改关系，须进入报告更正、撤回或重新签发等受控流程。具体审批级别留待权限和流程设计确认。
  - 申请与病例关系的建立、拆分、重复申请归并和重新关联，必须作为独立业务事实记录，并保留原始申请、原始病例、原始关系、新关系、原因、人员、时间、审核/批准信息、下游影响和相关质量事件。
  - 不得物理删除或无痕覆盖原关系，不得通过修改外部申请标识伪造关系，不得因病例或申请取消删除历史，不得因病例取消复用原病例身份。
- 本次确认边界：仅确认业务边界和追溯要求，不确定实体、聚合、数据库表、字段、接口或完整状态机。

### 4.2 BD-P04-003：患者与就诊权威来源、快照和冲突处理

- 决策项编号：BD-P04-003
- 决策主题：患者与就诊权威来源、快照和冲突处理
- 原始决策引用：BD-P04-003（来源：P04 业务决策待确认台账）
- 主要场景：SCN-PIS-001、SCN-PIS-003
- 原始问题引用：Q-SCN-PIS-001-03、Q-SCN-PIS-003-05
- 台账阻塞的后续工作：P05-001 核心领域对象识别
- 已确认事实：
  - 患者身份通常来自医院权威系统；PIS 不管理完整就诊生命周期；外部患者信息不能盲目覆盖本地已确认事实；报告和病例需要保留可追溯的患者/就诊上下文。
- 原待确认问题（已由本次确认结论覆盖）：
  - 患者和就诊的权威来源、入站快照、字段更新和冲突处理应如何划分？
- 候选方案：
  - 候选 A：外部系统对所有患者和就诊字段永久权威，PIS 不保留本地快照。
    - 比较：来源单一，但无法保留业务发生时的证据，也难以解释后续外部变更。
  - 候选 B：申请进入 PIS 后，由本地已确认记录永久权威，外部更新不再参与。
    - 比较：便于稳定追溯，但可能保留错误或过期身份，且丢失外部更正能力。
  - 候选 C：按字段和事件分层确定权威；保留原始外部快照，本地确认事实不能被静默覆盖，冲突进入受控处理。
    - 比较：能同时保留来源证据和本地医疗责任，但需要明确字段级规则和冲突责任。
- 原推荐方向：建议作为确认起点采用候选 C 的方向：分层权威、保留原始外部快照、保护本地已确认事实，并将冲突作为可追踪业务事件处理。
- 建议理由：该方向符合接口边界和医疗数据完整性要求，既不让 PIS 伪造患者主索引，也不让外部消息静默改变已经用于业务和报告的本地事实。
- 如果不采用建议方向的主要风险：若不保留快照或允许盲目覆盖，可能导致患者错配、报告上下文变化不可解释、外部更正无法安全落地。
- 对 P05 的影响：会阻塞患者/就诊/病例对象边界、报告快照和入站接口业务事实的确认。
- 业务确认结论：采用方案 C，按字段和业务事件分层确定权威来源，并保留患者、就诊及报告上下文快照。
- 最终结论：患者、就诊、外部标识和病理业务上下文保持概念区分；分层保留外部来源事实、PIS 当前参考信息、病例建立时业务快照和报告签发时版本快照；外部更新不得覆盖历史快照或已签发报告版本，冲突必须进入受控核对流程。
- 确认状态：已确认。
- 确认人：待补录。
- 确认日期：2026-08-05。

- 已确认权威来源和快照约束：
  - 外部医院系统负责提供患者和就诊主数据；患者身份默认以医院指定的患者主索引或患者身份权威系统为准，优先顺序由医院配置确定；没有患者主索引时由医院指定 HIS 或其他系统作为默认权威。
  - 患者身份核心字段至少可能包括外部患者标识、姓名、性别、出生日期、证件类型及证件号码等用于身份匹配的信息；具体字段范围留待配置确认。
  - 就诊信息默认由医院指定的就诊管理系统提供，通常为 HIS 或 EMR；不同字段可以来自不同系统，但必须配置来源优先级，不得运行时猜测权威来源。
  - 就诊信息至少可能包括外部就诊标识、就诊类型、门诊号或住院号、就诊科室、病区、床号、主治医生或申请医生以及入院、出院和就诊时间；具体字段范围留待配置确认。
  - PIS 对病理申请、病例、标本、取材、组织盒、组织处理、包埋、蜡块、切片、技术医嘱、诊断、报告、质量事件、档案和审计等病理业务事实负责；外部患者或就诊更新不得直接修改这些事实。
  - 采用字段级权威机制；每个可同步字段可以配置默认权威来源，冲突不得简单按最后到达消息覆盖；外部消息时间不等于业务事实时间；来源优先级不代表可以改写历史快照。
  - PIS 人工确认值不等于医院主数据已被修改；本地修正只对病理业务上下文生效，必须记录原因、人员、时间和依据，必要时反馈医院权威系统。
  - 保留外部接收来源、外部患者标识、外部就诊标识、接收时间、外部业务时间、关键患者和就诊信息及消息或业务事实追溯标识。
  - 病例建立时必须保存当时用于确认病例身份和业务归属的患者、就诊快照；后续变化不得覆盖该快照。
  - 每个正式报告版本必须保存签发时使用的患者、就诊及病例上下文快照，与报告版本绑定，签发后不可修改，并与报告 PDF 或其他报告载体保持一致。
- 已确认外部更新和冲突约束：
  - 外部更新可以进入 PIS 当前参考信息，但必须保留来源和更新时间，不得覆盖病例建立快照、报告签发快照、已签发报告版本或病理人员已确认的高风险信息。
  - 信息一致时可以自动接收；存在冲突或无法确定新旧关系时，必须进入受控核对，不得按到达顺序覆盖。
  - 高风险身份冲突必须人工核对并保留前后信息、处理人员、依据和结论，原则上阻止病例继续向诊断和报告签发推进；已建立病例时评估标本和下游对象，已签发报告时评估更正、撤回或重新签发，必要时触发质量事件。
  - 高风险冲突至少包括外部患者标识、姓名、性别、出生日期、证件号码、就诊归属不一致，患者与申请/标本/病例关系冲突，以及疑似错误患者或错误就诊。
  - 中风险业务归属冲突按字段和业务阶段决定是否阻断，不得影响患者身份核对；重要变化须由授权人员确认，报告签发前完成影响报告内容的处理。
  - 中风险冲突可包括科室、病区或床号、申请医生、就诊类型、就诊时间或业务归属疑问；低风险变化可包括联系电话、地址、当前床位等不影响身份和报告结论的参考信息。
  - 低风险参考信息可以更新当前参考信息，但不修改历史病例和报告快照。
  - 紧急业务是否允许在受控临时身份下接收标本留待后续流程确认；身份冲突解除前不得正式签发报告。
- 已确认签发后、患者合并拆分和审计约束：
  - 正常主数据变化不生成新报告版本、不修改历史报告；报告显示信息确有错误时必须形成受控报告更正版本并保留原版本；错误患者、错误就诊、错误申请或错误标本必须停止继续使用错误版本，进入撤回、关系纠正和重新签发流程并触发质量评估。
  - 第一版接收患者合并/拆分通知，保存来源、时间和外部关系，识别受影响申请、病例和报告，提供人工核查依据，保留变更前外部标识关系；不得自动删除、自动重挂已签发报告或执行破坏性自动合并。
  - 第一版不承担医院级患者主索引合并、自动去重、无人工确认的病例批量迁移或已签发报告自动重新归属。
  - 冲突处理必须使用可追溯个人账号，不得共享账号；记录原值、新值、来源、冲突类型、处理人员、时间、依据、受影响对象及是否触发报告处理或质量事件。系统管理员不得因系统管理权限自动获得患者身份业务确认权限。
- 本次确认边界：仅确认业务边界和追溯要求，不确定实体、值对象、聚合、数据库表、字段、接口或完整状态机；具体字段范围、处理角色和审批级别留待后续配置、权限和流程设计确认。
- P05 设计输入：患者与就诊分属不同概念并保留内部身份/外部标识关系；外部来源事实、当前参考信息和业务快照分层；病例建立和报告签发分别保存快照；外部更新不得修改历史快照或已签发报告；字段级权威可配置；身份冲突作为独立受控业务事实；患者合并拆分第一版仅支持接收、识别、追溯和人工处理；PIS 不承担医院级患者主数据治理。

### 4.3 BD-P04-008：标本容器、标本和申请的边界

- 决策项编号：BD-P04-008
- 决策主题：标本容器、标本和申请的边界
- 原始决策引用：BD-P04-008（来源：P04 业务决策待确认台账）
- 主要场景：SCN-PIS-004
- 原始问题引用：Q-SCN-PIS-004-01
- 台账阻塞的后续工作：P05-001 核心领域对象识别
- 已确认事实：
  - 标本容器是物理承载物，标本是生物材料，二者不能混用；一个申请可以包含多个容器；一个病例可以有多个标本；标本必须参与接收和追溯，容器是否建立独立追踪身份尚待确认。
- 待确认问题：
  - 申请、标本容器和标本是否建立分层独立身份，以及多容器、多标本和容器替换如何表达？
- 候选方案：
  - 候选 A：申请、容器、标本分别建立身份并显式关联。
    - 比较：能够表达一申请多容器、容器与材料差异以及交接核对，但对象和规则较多。
  - 候选 B：容器即标本，只建立一个身份。
    - 比较：操作看似简单，但无法表达承载物和生物材料的差异、拆分和异常。
  - 候选 C：先建立标本身份，容器只作为物理载体记录，不承担独立业务身份。
    - 比较：可表达材料，但难以支撑容器级扫码、交接、数量和标签追溯。
- 历史原推荐方向（本次确认前）：建议采用候选 A，即申请、容器和标本分别建立身份并显式关联；该历史推荐保留用于说明本次业务修正背景，不作为最终结论。
- 最终确认方向：采用方案 C 增强版：病理申请、病理病例和标本保持独立业务身份；容器默认作为标本的物理承载信息，不作为所有医院和所有业务场景下必须存在的独立核心业务对象；医院有明确需求时再启用独立容器管理扩展。
- 确认理由：该方向保留标本作为核心追溯对象，同时避免把容器级管理强制前置到所有医院；能够覆盖默认单容器承载、同源材料分装、多材料拆分和医院差异化容器管理。
- 本次业务修正背景：业务负责人基于实际登记流程确认，容器无需在所有医院和所有业务场景下默认建立独立核心身份；容器的物理承载位置、条码贴附位置和是否启用容器级追踪，不改变标本作为核心来源对象的原则。
- 方案 C 增强版已确认业务约束：
  - 病理申请、病理病例和标本保持独立业务身份，默认来源链为“病理申请 → 病理病例 → 标本 → 取材活动 → 组织盒 → 组织处理 → 包埋 → 蜡块 → 物理切片”。
  - 标本至少记录所属病例、来源患者、来源部位、标本类型、左右侧/方向/近远端信息、标本业务编号或条码、实物接收结果、容器和固定液信息、接收异常及后续物理产物来源关系。
  - 容器默认作为标本或标本接收记录中的物理承载信息，记录容器类型、数量、固定液、标签状态、破损/泄漏、外部描述和包装情况；容器变化不得改变标本身份。
  - 更换标本瓶、标本袋或其他承载物，原则上记录为标本实物处理或接收事件，不重新生成标本身份。
  - 贴附在容器上的条码默认作为标本条码使用，但申请条码不等于标本条码，标本条码和外部条码也不等于 PIS 内部身份。
  - 默认一个病例可以包含多个标本，一个标本通常由一个物理容器承载，但不得把一个标本只能有一个容器写死为不可变规则。
  - 同一标本分装到多个容器时，后续可按容器数量和分装说明、同源标本关系或启用容器扩展管理进行表达，具体方案待流程设计确认。
  - 一个容器中多个材料的处理应依据材料是否具有独立病理意义；同部位同类型碎片可作为一个标本，不同部位、方向或需要独立诊断的材料应拆分为独立标本，并保留原始接收和来源信息。
  - 容器级扫码、交接、物流追踪、分批到达、独立退回或补送、跨多个容器承载一个标本、一个容器承载多个独立标本等能力，作为医院可配置的独立容器管理扩展，不作为核心流程强制前置条件。
  - 核心接收事实必须区分标本预登记、标本实物到达、标本身份核对、标本正式接收和标本接收合格；未启用容器扩展时不强制建立独立的容器登记、容器接收和容器内容确认链。
  - 容器标签缺失、破损、泄漏、固定液不符等默认记录为标本接收异常，必须记录异常类型、实物状态、处理人员、处理时间、处理结论、是否允许继续处理、是否影响诊断及是否触发质量事件。
  - 容器异常不自动改变标本身份；患者或标本来源无法确认时，必须阻止正常取材和报告签发。
- 业务信息灵活修改与受控纠错通用原则（已确认）：
  - 系统应支持错误、遗漏和变化信息的修正；可修改不等于可无痕覆盖，高权限不等于无限制权限，纠正业务信息不等于删除历史事实。
  - 普通系统管理员仅负责用户、权限、参数、技术运维和系统可用性，不得仅凭技术权限修改患者身份、病例归属、标本来源、组织盒/蜡块/切片来源、诊断、已签发报告或质量事件结论。
  - 病例纠错应由具有业务责任的个人账号执行，可由医院配置病理业务纠错管理员、病理科管理人员、质量管理人员、高级登记人员或诊断业务负责人承担；禁止共享高权限账号。
  - 普通业务修改适用于尚未形成重要下游事实的信息；已被后续业务使用的信息必须建立纠正记录或重新关联，并记录原值、新值、原因、人员、时间、复核、下游影响、实物核对、标签处理、诊断/报告影响和质量事件影响。
  - 患者身份、病例患者归属、标本来源、已取材标本、已形成组织盒/蜡块/切片后的来源、报告草稿关键病例信息、已签发报告信息和批量修改属于高风险纠错，应具备高权限、明确理由、二次身份确认、必要复核/审批、影响分析和完整审计。
  - 修改能力应随业务阶段逐步收紧：病例建立前可较灵活修正；病例建立后需重新核对患者、就诊、申请、病例和预登记标本；标本接收后需核对实物、标签和交接；取材或物理产物形成后需联动评估下游对象；报告草稿形成后需通知诊断人员并重新核对；正式报告签发后不得直接编辑或覆盖。
  - 已签发报告相关错误必须通过报告更正、补充、撤回或关系纠正后重新签发等版本生命周期处理，原报告版本永久保留。
  - 修改方式应区分更新当前值、建立纠正记录、重新关联、新建版本和作废而不删除；关系纠正必须保留原关系、新关系及变更过程，作废对象不得物理删除或静默复用编号。
  - 任何账户都不得物理删除已形成业务事实的病例、标本接收历史、组织盒/蜡块/切片来源、已签发报告版本或审计记录；不得通过数据库直改、修改时间/人员/编号或修改外部标识伪造原始事实。
  - 紧急纠错必须使用个人账号，填写紧急原因和受影响病例，记录修改前后内容，通知相关责任人员，自动形成待复核事项，并在规定时间内完成复核和关闭；紧急纠错不是绕过审计和审批的后门。
  - 权限至少区分普通字段编辑、病例关键字段纠错、患者身份纠错、标本来源纠错、物理产物来源纠错、报告更正、报告撤回、批量修改和审计查询，并支持按院区、科室、业务类型、病例范围和时间范围控制数据范围。
  - 对本决策而言，容器默认作为标本实物信息时，容器类型、数量、固定液和状态可以受控修改，但必须保留容器更换前后信息和历史处理记录；启用独立容器管理时，容器与标本关系纠正必须保留原关系并评估取材、组织盒、蜡块和报告影响。
  - 外院蜡块和外院切片应作为独立外部物理材料识别，保留外部机构、外部编号、材料类型、当前申请/病例关系、已知来源标本和来源不完整说明，不得伪造完整来源链。
  - 标本信息允许授权人员受控修改；已形成组织盒、蜡块或切片后必须评估下游来源链，已形成报告草稿后必须通知并重新核对诊断内容，已签发报告后必须通过关系纠正、报告更正、撤回或重新签发处理。
- 对 P05 的影响：会阻塞标本接收、取材、组织盒来源以及所有物理产物的来源链设计；P05 必须把标本作为核心独立对象，把容器管理作为可配置扩展，并将受控纠错原则作为统一设计输入。
- 最终确认结论：病理申请、病理病例和标本保持独立业务身份；标本是核心独立业务对象；容器默认作为标本实物承载信息或接收信息，不作为所有医院强制存在的独立核心业务对象；独立容器管理为医院可配置扩展；容器更换不改变标本身份；标本条码、申请条码、外部条码和 PIS 内部身份保持区分；一个病例可以包含多个标本，一个标本通常由一个容器承载但不固化为不可变一对一；多材料按独立病理意义拆分并保留来源；标本接收事实分层记录；容器异常默认作为标本接收异常处理；业务信息允许灵活但受控纠错，历史事实和已签发报告版本不得被无痕覆盖。
- 受控纠错原则文档：`docs/project/controlled-business-correction-principles.md`。
- 本次确认边界：仅确认业务对象边界、来源追溯、容器扩展和受控纠错原则，不确定实体、聚合、数据库表、字段、接口、页面或完整状态机。
- 确认状态：已确认。
- 确认方案：方案 C 增强版。

### 4.4 BD-P04-013：标本身份、扫码和核对规则

- 决策项编号：BD-P04-013
- 决策主题：标本身份、扫码和核对规则
- 原始决策引用：BD-P04-013（来源：P04 业务决策待确认台账）
- 主要场景：SCN-PIS-010、SCN-PIS-012
- 原始问题引用：Q-SCN-PIS-010-01、Q-SCN-PIS-010-02、Q-SCN-PIS-012-04
- 台账阻塞的后续工作：P05-001 核心领域对象识别
- 已确认事实：
  - 标本是具有来源部位和病例归属的生物材料；需支持扫码和人工核对；一个病例可有多个标本；容器关系不能替代标本身份。
- 待确认问题：
  - 标本身份何时建立，扫码和人工核对需要核对哪些身份，接收前后如何处理暂存或不完整信息？
- 候选方案：
  - 候选 A：标本独立识别并在接收/核对时强制确认来源容器、病例和来源部位。
    - 比较：追溯最清晰，但需要处理信息不完整和异常接收。
  - 候选 B：标本身份完全由容器号推导，不建立独立标本身份。
    - 比较：实现简单，但容器变化或一容器多材料时会丢失材料层级。
  - 候选 C：接收后才创建标本身份，接收前只保留不可追溯的临时记录。
    - 比较：能简化前置录入，但会造成早期交接和异常证据断裂。
- 原推荐方向：候选 A——标本独立识别并在接收/核对时确认来源容器、病例和来源部位；如果业务存在接收前暂存，应采用可追溯的受控临时状态，不能使用无来源的临时记录替代标本身份。
- 最终确认方向：方案 A 增强版——标本在首次进入 PIS 管理范围时建立稳定、可追溯的独立身份，通过预登记、实物到达、核对、正式接收和接收合格等业务事实逐步完成确认；标本身份与标本业务状态保持区分。
- 确认理由：标本是后续取材和来源链的直接基础，必须尽早建立稳定身份，同时支持信息不完整、异常接收、扫码失败、暂存和后续受控纠错。
- 如果不采用增强方向的主要风险：若等到正式接收后才创建标本身份，或完全依赖容器号、条码或外部标识推导，可能导致接收前交接、实物暂存、数量差异、身份冲突、拒收退回和后续补录无法稳定追溯。
- 方案 A 增强版已确认业务约束：
  - 标本身份应在 PIS 首次需要追踪某份具体送检材料时建立，适用于外部申请明确标本、人工预登记、实物首次扫码/交接/登记、未预登记实物到达以及身份尚未完全明确但需要受控暂存的情况。
  - 标本预登记具有稳定 PIS 内部身份，但不代表实物已到达、身份已核对或正式接收；至少记录可获得的申请、病例、患者/就诊上下文、预期材料、来源部位、方向信息、类型、外部标识、信息来源、建立人员/服务身份和建立时间。
  - 信息不完整时允许空缺或待确认标记，不得猜测填写。
  - 身份不明实物允许建立可追溯临时标本记录，必须记录到达时间、存放位置、人员、可见标签、外部条码、包装/固定液/实物状态、可能关联对象、未确认事项、异常原因和后续责任人。
  - 临时身份不等于正式确认；身份未确认前不得正常取材、生成正式组织盒、进入诊断或签发正式报告。
  - 标本正式接收前至少核对患者、申请、病例、标本、名称/来源部位、左右/方向/近远端、标本条码/业务标识、实物数量、标签一致性、固定液和实物状态；医院可按业务类型增加核对项。
  - 标本身份和标本业务状态必须区分，至少区分预登记、实物到达、身份待核对、身份已确认、正式接收和接收合格；本次不确定完整状态机。
  - 扫码是优先核对方式，但不是所有情况下唯一方式；扫码结果必须关联具体标本并判断存在性、唯一性、归属、一致性和是否被其他实物使用。
  - 条码损坏、无法识别、外部未生成条码、紧急送检、外院材料、设备故障或确认需要重打/重绑时允许人工处理；必须使用实名账号、记录原因和原条码，人工核对患者、病例、标本和来源部位，必要时由第二人复核。
  - 申请条码、标本条码、外部标本条码和 PIS 内部身份保持区分；条码重打、损坏、更换或重绑不得改变标本身份，原条码和重绑历史不得被覆盖。
  - 允许批量扫码，但每个标本必须单独记录扫码、核对、接收、异常、人员和时间结果；单个失败不得自动改变其他标本结果，整批成功不得掩盖单个异常。
  - 不要求所有标本一律双人核对；患者冲突、条码错配、无标签、人工重绑、关系重关联、身份不明实物解除暂存、已形成下游对象后的纠错等高风险场景应按配置要求双人复核。
  - 患者无法确认、申请/病例/实物无法建立可靠关系、来源部位或方向存在医疗风险冲突、条码指向其他患者/病例、实物与标签明显不一致或无法确定业务归属时，必须阻断正式接收或后续正常处理，并进入暂存/异常流程。
  - 联系方式缺失、非关键临床信息不完整、轻微容器破损、固定液待补充或低风险数量差异可以按医院规则条件接收，但必须记录异常、处理意见、责任人、期限和后续影响。
  - 标本信息不得永久锁死；普通字段可由授权人员在早期修改，患者/病例归属、来源关系、已使用条码关系以及已影响取材、诊断或报告的字段必须由高权限业务角色受控纠错。
  - 已取材、组织盒/蜡块/切片/数字切片或报告形成后，修改必须核查相应下游对象、标签、批次、扫描、质控、诊断和报告影响；已签发报告不得直接修改，必须进入更正、撤回或重新签发流程。

- 原始决策引用：BD-P04-020（来源：P04 业务决策待确认台账）

- 原待确认问题（本次已纳入确认范围）：
  - 组织盒是否作为独立物理业务对象记录，其身份、用途、排序、位置和实际生成数量如何与取材活动、预分配蜡块业务单元及后续物理蜡块形成关联？
- 候选方案：
  - 候选 A：每个物理组织盒独立识别，并记录来源标本、取材活动、用途和位置。
    - 比较：来源和后续处理最清晰，但需要维护组织盒的独立生命周期。
  - 候选 B：只在取材活动中保存组织盒号列表，不建立组织盒独立对象。
    - 比较：录入较快，但无法可靠承载组织盒级位置、处理、作废和返工追踪。
  - 候选 C：同时记录计划组织盒和实际确认的物理组织盒。
    - 比较：能表达计划与实际差异，但会增加两类记录的关系和确认规则。
- 原推荐方向（确认前，未确认）：候选 A——每个物理组织盒独立识别，并记录来源标本、取材活动、用途和位置；只有在确认存在稳定的计划/实际差异需求时，才在不合并物理身份的前提下补充候选 C 的受控计划记录。
- 原推荐理由：组织盒是“标本 → 取材活动 → 组织盒 → 组织处理”的关键断点，独立身份能防止将取材记录误当成物理产物。
- 原推荐方向的主要风险说明：若只保存列表，无法在组织处理、包埋、位置变更和返工时确认具体物理组织盒。
- 本次修正过程：根据实际取材流程，将组织盒与物理蜡块的对象身份和形成事实继续区分，同时允许取材阶段预分配蜡块业务编号并打印在组织盒标签上；该编号形成过程不等于物理蜡块形成过程。
- 正式确认结论（方案 A 增强版）：
  - 每个实际形成并投入使用的物理组织盒具有独立、稳定的内部身份；组织盒必须关联明确来源标本和具体取材活动。
  - 一个标本允许形成多个组织盒，一个取材活动允许形成多个组织盒；组织盒承载取材后的组织材料并进入组织处理。
  - 组织盒与物理蜡块是不同物理对象，必须分别保留内部身份、形成事实、处理事实和异常事实。
  - 物理蜡块只有在组织处理完成并完成包埋后才实际形成。
  - 取材阶段执行“添加蜡块”时，可以创建待形成蜡块的业务单元，分配蜡块序号或蜡块业务编号；蜡块业务编号通常可以采用“病理号-蜡块号”。
  - 预分配蜡块业务编号可以打印在组织盒标签上，组织盒进入组织处理后，包埋形成的物理蜡块可以继续沿用该业务编号。
  - 组织盒内部身份、物理蜡块内部身份、蜡块业务编号和条码内容保持区分；组织盒与物理蜡块的业务编号相同，不代表组织盒与物理蜡块是同一个物理对象。
  - 蜡块业务单元、预分配蜡块号和实际物理蜡块形成事实必须保持区分；编号生成时间可以早于物理蜡块形成时间。
  - 组织盒、组织处理、包埋和物理蜡块的来源链为：病理病例 → 标本 → 取材活动 → 组织盒 → 组织处理 → 包埋 → 物理蜡块 → 物理切片。
