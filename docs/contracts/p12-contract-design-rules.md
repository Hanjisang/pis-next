# P12 全病理API与接口契约设计规则

文档状态：P12已基线化
适用范围：常规组织病理、术中冰冻、妇科/非妇科/穿刺细胞病理、细胞蜡块、分子病理、外送检测和多模态综合诊断。
正式编号：`P12-SCH-XXX`、`P12-API-XXX`、`P12-HIF-XXX`、`P12-EVC-XXX`、`P12-ERR-XXX`、`P12-COMP-XXX`、`P12-IRISK-XXX`。

## 1. 接口边界

P10已确认模块化单体、可靠事件/任务协调、外部防腐适配器、文件与数字材料能力，以及本地事实与外部状态分层。仓库未确认REST、OpenAPI、AsyncAPI、HL7、FHIR、DICOM或其他传输协议。因此本批次定义产品中立的业务契约，不把内部应用能力强制变成远程HTTP，也不生成机器可读协议文件。

## 2. P12设计规则

### P12-RULE-001：契约来源可追溯

每个正式API操作、医院接口、事件和主要Schema字段至少追溯到需求、验收准则、对象、聚合、不变量、流程、异常、状态机、架构模块、事务、架构事件、逻辑表或ADR。无来源能力不得成为正式契约。

### P12-RULE-002：内部API表达应用能力

内部API是模块公开的业务应用能力，不等于进程内方法、远程服务、HTTP端点或SDK。15个模块不机械对应15个远程服务。

### P12-RULE-003：命令和查询分离

命令表达意图、触发事务、形成事实并接受守卫；查询只读取业务信息，不产生状态变化或隐式副作用。

### P12-RULE-004：禁止数据库结构直出

接口字段按业务语义命名；P11表、列、外键和内部状态字段只作为映射证据，不成为外部资源、请求字段或响应契约。

### P12-RULE-005：禁止万能CRUD

不得使用万能对象、任意记录更新、任意字段PATCH、统一保存、统一查询或统一状态赋值能力代替正式业务命令。

### P12-RULE-006：状态转换必须是业务事件

状态变化只能由接收、确认、签发、撤回、交接、结果有效性确认等正式业务行为触发；不得暴露`setStatus`、`updateStatus`或目标状态赋值。

### P12-RULE-007：聚合写入归属唯一

命令由拥有聚合的P10主责任模块处理；其他模块使用公开应用能力、受控查询或不可变事件，不直接修改聚合内部事实。

### P12-RULE-008：身份、编号和外部标识分离

内部稳定身份、申请号、病例号、标本号、蜡块号、玻片号、报告版本号、文件身份、外部标识和来源消息标识分别表达，不复用一个通用ID。

### P12-RULE-009：患者和就诊保持外部上下文

接口只接收外部引用、来源系统、业务时点快照和本地病例关系；不把PIS设计成患者主数据维护接口。

### P12-RULE-010：契约字段不复制数据库列

Schema字段必须有业务含义、来源、基数、必填性、时间语义、更新语义和兼容规则；数据库映射只能作为实现输入。

### P12-RULE-011：字段定义完整

每个正式字段必须记录名称、中文名称、逻辑类型、基数、必填/条件必填、业务含义、来源、敏感等级、代码来源、时间语义、身份语义、更新语义、版本兼容和错误行为。

### P12-RULE-012：条件必填可判定

条件必填必须写明业务类型、来源、操作或状态、判定责任和缺失后的拒绝、隔离或待复核结果，不使用“按情况”或“按需”。

### P12-RULE-013：代码值有来源

代码只来自术语、P08状态机、已确认决策、医院字典、设备字典、外部标准或受控配置；P12不创造医学代码值。

### P12-RULE-014：时间语义明确

业务发生时间、系统接收时间、外部发生时间、创建时间、确认时间、签发时间、业务日期和时区分别表达；不使用含义不明的time或date。

### P12-RULE-015：写入操作必须幂等

每个可重复写入操作必须声明幂等键、作用域、载荷摘要、首次结果、同载荷重复、不同载荷重复、处理中重复、并发处理、保留期参数引用和人工解除入口。

### P12-RULE-016：外部消息优先来源幂等

外部入站消息使用来源系统、来源消息标识、消息版本、外部业务标识和载荷摘要；不得只按患者姓名、病理号或时间判重。

### P12-RULE-017：预期版本控制并发

修改聚合当前事实的命令必须声明预期业务版本、冲突错误、重读要求、可否安全重试和禁止静默覆盖规则；不规定数据库版本字段名。

### P12-RULE-018：错误模型分层

错误至少区分契约校验、认证、授权、对象不存在、业务冲突、版本冲突、非法转换、幂等冲突、患者安全阻断、外部依赖、文件、业务确认、对账和内部错误。

### P12-RULE-019：传输和业务结果分离

请求接收、校验通过、本地处理成功、事件形成、投递、外部技术应答、外部业务生效和对账一致分别表达。

### P12-RULE-020：外部失败不回滚本地事实

报告签发、材料形成、有效结果确认等本地事实提交后，外部投递或确认失败只能形成投递、异常、重试、补偿或对账事实。

### P12-RULE-021：报告固定具体版本

报告接口、文件和综合报告只能引用具体报告版本；补充、更正、撤回和重新签发分别形成新的生命周期事实。

### P12-RULE-022：结果层次分离

分子和设备契约必须区分原始结果、质控结果、有效性确认、有效检测结果、医学判读和正式报告。

### P12-RULE-023：文件和普通业务载荷分离

PDF、数字切片和大型外部报告使用文件身份、版本、元数据、摘要、传输引用、访问授权和业务引用；二进制不嵌入普通业务JSON。

### P12-RULE-024：事件表达已发生事实

事件使用事实语义，不作为远程命令；事件数量由跨模块责任和外部协作产生，不由93个状态转换机械产生。

### P12-RULE-025：事件不可变

已发布事件不可修改；纠错、补充和撤回通过新事实、新版本或新事件表达。

### P12-RULE-026：事件版本兼容

事件类型、版本、Envelope、字段新增/弃用、旧消费者处理、重放范围、乱序、迟到和重复语义必须明确。

### P12-RULE-027：敏感数据最小化

接口和事件只携带完成业务所需的患者、材料、诊断、报告和外部信息，不在所有事件复制完整患者或报告正文。

### P12-RULE-028：人工、代理、服务和设备身份分离

实际操作者、业务责任人、代理关系、服务身份、设备身份和外部系统身份分别表达；服务或设备身份不得成为医学签发责任人。

### P12-RULE-029：审计上下文可信形成

认证主体、服务身份、接收时间、来源、授权结果、目标对象和处理结果由可信系统上下文形成；客户端自报只能作为业务说明或外部时间输入。

### P12-RULE-030：医院差异由适配器隔离

核心契约使用规范化语义，医院字段、状态、字典、协议和错误通过14个P10适配器映射，不污染核心模型。

### P12-RULE-031：机器规范不得超出正文

若后续存在正式协议决策，机器规范必须与Markdown字段、必填、错误、版本和安全语义完全一致；示例不构成正式规则。

### P12-RULE-032：未确认参数不硬编码

P09-PARAM-001至P09-PARAM-018全部保持未确认状态。分页、超时、文件大小、重试、幂等保留、对账周期、容量、RPO和RTO只引用参数编号和配置边界，不写虚假数值。

### P12-RULE-033：编号稳定

Schema使用`P12-SCH-XXX`，内部API使用`P12-API-XXX`，医院接口使用`P12-HIF-XXX`，事件契约使用`P12-EVC-XXX`，错误使用`P12-ERR-XXX`，兼容规则使用`P12-COMP-XXX`，风险使用`P12-IRISK-XXX`。21个P10事件继续使用原`P10-EVT-XXX`编号。

## 3. 逻辑类型和基数

契约使用产品中立逻辑类型：`InternalId`、`BusinessNumber`、`ExternalIdentifier`、`ControlledCode`、`ShortText`、`LongText`、`StructuredDocumentReference`、`UtcInstant`、`LocalBusinessDate`、`TimeZoneIdentifier`、`Boolean`、`IntegerCount`、`DecimalQuantity`、`FileReference`、`BinaryDigest`、`VersionNumber`、`ConcurrencyVersion`和`Cursor`。基数使用`1`、`0..1`、`0..N`和`1..N`。

## 4. 机器规范状态

仓库没有正式OpenAPI、AsyncAPI或传输协议决策，故本批次不创建`docs/contracts/spec`。Markdown契约是P12权威；后续只有在协议、版本和目标边界正式确认后，才从本文件、公共Schema和接口目录生成机器规范。
