## 1. 文档目的

本文规定 PIS Next 文档、代码、数据库、API 和界面中术语的使用规则。

目标是确保同一业务对象在不同层面保持统一含义。

---

## 2. 核心对象禁止混用规则

### RULE-TERM-000：三层区分规则

PIS Next 必须区分以下三层概念：

```text
真实物理过程
≠ PIS 核心业务对象
≠ 系统操作留痕
```

- 真实物理过程描述材料在现实中的变化，例如取材、脱水、包埋、切削、染色和封片；
- PIS 核心业务对象描述需要持续追溯的业务事实，例如标本、蜡块业务记录、玻片和报告版本；
- 系统操作留痕描述谁在何时以何种方式完成了业务动作、责任转移或异常处理。

真实物理过程不自动等于新的核心业务对象，也不自动要求创建独立页面、人工点击或状态机节点。只有在产生新的可追溯材料、责任转移、患者安全或诊断报告影响、异常或质量事实时，才需要建立相应的业务记录或操作责任记录。

---

### RULE-TERM-001：患者不等于病例

错误示例：

```text
患者状态：已切片
````

正确表达：

```text
病理病例当前展示状态：处理中
某切片状态：已完成
```

患者本身不具有病理制片状态。

---

### RULE-TERM-002：申请不等于病例

病理申请表示临床业务请求。

病理病例表示 PIS 中实际管理的病理诊疗业务对象。

不得使用一个对象同时表示申请、病例、医嘱和收费记录。

---

### RULE-TERM-003：容器不等于标本

容器是物理承载物。

标本是送检生物材料。

不得只设计“标本表”同时承载：

* 瓶子；
* 标签；
* 组织；
* 部位；
* 交接；
* 接收结果。

---

### RULE-TERM-004：标本不等于蜡块

标本是患者来源材料。

蜡块业务记录是在取材阶段执行“添加蜡块”时建立的 PIS 核心业务记录，可以同时分配蜡块号；物理石蜡块在组织处理和包埋完成后才形成。

蜡块业务记录、蜡块号和实际物理石蜡块形成事实必须保持可追溯关系，不得将蜡块号保存在标本编号字段中代替蜡块业务记录。

---

### RULE-TERM-004A：组织盒不等于蜡块

组织盒是取材后承载组织材料并进入组织处理的物理承载物，默认不是所有医院都必须启用的独立核心业务对象。

蜡块业务记录在取材阶段建立并分配蜡块号；物理石蜡块在包埋完成后形成，通常继续沿用原蜡块业务记录和蜡块号。

必须遵守：

1. 取材阶段可以创建蜡块业务记录并分配蜡块号，不得因此表述为物理蜡块已经形成；
2. 应使用“将组织材料放入组织盒”表达取材材料承载关系；
3. 组织盒标签可以打印预分配的蜡块号；
4. 组织盒进入组织处理，组织处理和包埋记录应关联明确的蜡块业务记录；
5. 包埋完成后才形成物理石蜡块，通常继续沿用原蜡块业务记录和蜡块号；
6. 组织盒与物理石蜡块必须具有可区分的物理身份和形成事实；
7. 组织盒标签上的蜡块号与物理石蜡块的业务编号即使相同，也不得合并两个物理对象；
8. 只有医院明确需要容器级扫码、交接、物流或自动化管理时，才启用组织盒独立追踪扩展；
9. 后续场景、流程、领域模型、数据库和接口设计必须遵守该术语边界。

物理过程链为：

```text
标本
→ 取材活动
→ 组织盒
→ 组织处理
→ 包埋
→ 物理石蜡块
→ 组织切片
```

PIS 核心业务链为：

```text
病理病例
→ 标本
→ 蜡块业务记录
→ 玻片
→ 报告
```

---

### RULE-TERM-005：蜡块不等于切片

一个蜡块业务记录或实际物理石蜡块可以产生多张组织切片和多张玻片。

组织切片是从物理石蜡块切下的薄层组织材料；玻片是承载组织切片并进入后续技术或诊断的业务对象。不得在蜡块记录中只保存一个“切片号”来代表全部玻片。

---

### RULE-TERM-006：物理切片不等于数字切片

玻片是承载组织切片的物理病理材料及其 PIS 业务记录；载玻片是玻片使用的物理玻璃载体。数字切片是扫描形成的数字业务对象。

组织切片、载玻片、玻片标签和玻片业务记录都不等同于数字切片。

一张玻片可能存在多个数字切片扫描版本。

---

### RULE-TERM-007：报告不等于报告版本

报告表示完整生命周期。

报告版本表示一次不可变内容。

已签发报告内容必须落在具体报告版本中。

---

### RULE-TERM-008：报告版本不等于 PDF

PDF 是报告版本的一种固定表现文件。

报告版本还应包含结构化内容、签名、版本类型和业务元数据。

---

### RULE-TERM-009：临床医嘱不等于技术医嘱

临床医嘱由临床业务系统产生。

技术医嘱由病理科内部为诊断或技术处理需要产生。

两者可以关联，但不得混用。

---

### RULE-TERM-010：技术医嘱不等于技术任务

技术医嘱描述需要完成什么。

技术任务描述由谁、何时、在哪个执行上下文中完成。

具体关系后续设计。

---

### RULE-TERM-011：业务编号不等于内部 ID

病理号、蜡块号和切片号属于业务编号。

数据库内部 ID 应保持稳定且不受医院编号规则变化影响。

---

### RULE-TERM-012：业务状态不等于页面列表

“待取材列表”“待切片列表”属于查询视图。

不得直接将页面名称作为领域状态。

状态必须属于明确业务对象。

---

### RULE-TERM-013：返工不等于覆盖

重脱水、重包埋、重切、重染和重扫必须形成新的操作责任记录或技术结果记录；只有实际产生新的、独立可追溯的材料或业务对象时，才建立新的核心业务记录。

不得把原记录更新成最新结果后丢失历史。

---

### RULE-TERM-014：作废不等于删除

作废对象仍然存在，只是不再允许作为有效对象继续使用。

---

### RULE-TERM-015：撤回不等于删除报告

报告撤回必须保留已签发报告版本和撤回原因。

---

### RULE-TERM-000A：人工节点价值判断

真实物理过程只有在满足以下至少一项时，才需要在 PIS 中形成明确的业务记录或人工责任节点：

1. 产生新的可追溯材料或物理产物；
2. 发生业务责任转移；
3. 可能影响患者安全、诊断或报告；
4. 产生异常、质量事件或需要后续核查的事实。

如果以上条件均不满足，不得仅为了模拟设备或人工操作步骤而强制增加手工页面、按钮、状态或独立核心对象。批量操作、扫码、设备回传和系统自动处理可以在满足审计要求的前提下形成相应操作责任记录。

---

### RULE-TERM-004B：蜡块业务记录与物理石蜡块

以下表达为统一正确表达：

```text
取材时创建蜡块业务记录并分配蜡块号。
蜡块号可以打印在组织盒标签上。
物理石蜡块在包埋完成后形成。
系统通常继续沿用原蜡块记录和编号。
```

不得使用以下表达：

- 取材时物理蜡块已经形成；
- 组织盒就是蜡块；
- 组织盒号必须与蜡块号不同；
- 组织盒编号和蜡块编号必须采用不同编号策略；
- 包埋后必然创建一个新的核心蜡块对象。

业务编号相同不代表组织盒与物理石蜡块是同一个对象。

---

### RULE-TERM-004C：组织盒默认物理承载物

默认情况下，组织盒只表达取材后承载组织材料并进入组织处理的物理承载信息。它不是所有医院和所有业务场景下都必须存在的独立核心业务对象。

组织盒标签可以打印预分配的蜡块号。需要容器级扫码、交接、物流、分批到达或自动化管理时，才启用组织盒独立追踪扩展。启用扩展后，组织盒与蜡块业务记录、物理石蜡块之间仍必须保持明确关系。

不得把组织盒强制建模为物理蜡块，也不得因为组织盒更换、标签重打或承载关系调整而无痕创建或删除蜡块业务记录。

---

### RULE-TERM-005A：组织切片、制片、玻片、载玻片和玻片标签区分

必须区分以下概念：

- **组织切片**：从物理石蜡块切下的薄层组织材料；
- **制片**：选择来源蜡块、切取组织、将组织附着到载玻片并建立或确认玻片记录的业务操作；
- **玻片**：承载组织切片并进入后续技术或诊断的物理业务对象；
- **载玻片**：承载组织切片的物理玻璃载体，空白载玻片不等于完成的病理玻片；
- **玻片标签**：标识病例、蜡块、用途或业务编号的标签，属于标识物而不是玻片本身。

制片可以建立或确认玻片业务记录，但制片操作、组织切片、载玻片、玻片标签和玻片业务记录不得互相替代。

---

### RULE-TERM-005B：玻片标签与物理玻片

玻片标签可以在制片前打印或补打，用于引导后续制片；打印标签不代表物理玻片已经形成，标签上的业务编号也不等于玻片内部身份。

玻片业务记录的形成或确认应记录来源蜡块、制片类型、操作者、时间、数量和异常。标签作废、重打和重新绑定必须保留历史，不得用覆盖标签文本代替玻片关系纠错。

---

### RULE-TERM-006A：染色和封片

染色和封片是物理技术过程。常规染色、封片不必在 PIS 中强制拆成每一步都由人工确认的独立核心业务节点，可以通过批次记录、设备回传、技术完成记录或异常记录表达。

特殊染色、免疫组化、原位杂交等具有独立业务要求、结果或责任转移时，才按具体业务规则建立扩展记录。染色或封片不得改变玻片来源身份。

---

### RULE-TERM-014A：操作责任记录

操作责任记录是对业务动作或责任转移的统一追溯记录，至少能够表达：

- 作用对象；
- 操作类型；
- 操作人员或执行设备；
- 操作时间；
- 结果或处理结论；
- 异常及后续责任。

操作责任记录可由取材、脱水、包埋、制片、标签打印、技术完成、诊断任务分配、诊断、审核、签发和纠错等动作产生。它不是普通系统日志，也不要求每个物理步骤都建立独立页面或核心对象。

---

### RULE-TERM-014B：诊断任务分配

诊断任务分配是将病例、玻片或明确诊断范围交给具体诊断人员或诊断责任组的业务责任转移记录。至少应记录分配人员、接收人员、分配时间和重新分配历史。

诊断任务分配不等于诊断记录、复核记录或报告签发。重新分配不得无痕覆盖原责任关系。

---

## 3. 推荐统一用词

| 推荐用词   | 可接受同义词  | 不推荐用词 | 原因         |
| ------ | ------- | ----- | ---------- |
| 病理申请   | 病理申请单   | 申请病例  | 混淆申请与病例    |
| 病理病例   | 病例      | 患者记录  | 混淆患者与业务病例  |
| 标本容器   | 标本瓶、标本袋 | 标本    | 混淆容器和材料    |
| 标本     | 检材      | 样本瓶   | 混淆标本和容器    |
| 取材     | 大体取材    | 处理标本  | 语义过宽       |
| 组织盒   | 取材盒、脱水盒、Cassette | 标本容器、蜡块 | 默认是物理承载物；是否独立追踪由医院配置 |
| 组织盒号 | 取材盒号、组织盒标签编号 | 将组织盒号强制设为独立编号 | 标签可以打印预分配蜡块号，但对象身份不同 |
| 蜡块业务记录 | 蜡块、石蜡块记录 | 标本块 | 取材时建立，可在包埋后形成物理石蜡块 |
| 物理石蜡块 | 石蜡块 | 组织盒 | 包埋完成后形成的物理产物 |
| 组织切片 | 切下组织、tissue section | 物理切片 | 指从蜡块切下的组织材料 |
| 制片 | 切片制作、slide preparation | 切片状态 | 指将组织切片附着到玻片的业务操作 |
| 玻片 | 病理玻片、physical slide | 载玻片、数字切片 | 指承载组织切片的物理业务对象 |
| 载玻片 | 玻璃片、空白玻片 | 玻片记录 | 指物理玻璃载体，空白时不等于完成玻片 |
| 玻片标签 | 玻片标识、标签 | 玻片、玻片号 | 标签可以先打印，不代表物理玻片已经形成 |
| 数字切片   | WSI     | 切片文件  | 文件与数字业务对象不同  |
| 真实物理技术流程 | 实物流程 | 系统状态机 | 真实过程不自动等于 PIS 节点 |
| PIS 核心技术流程 | 技术业务链 | 设备步骤清单 | 只保留需要追溯的业务事实 |
| 操作责任记录 | 执行记录、责任留痕 | 普通日志 | 记录业务动作和责任，不等同于系统日志 |
| 诊断任务分配 | 诊断派工、诊断责任转移 | 诊断结论 | 分配责任不等于完成诊断 |
| 技术完成 | 技术处理完成 | 诊断完成、报告签发 | 仅表示诊断所需技术材料已具备 |
| 技术医嘱   | 科内技术医嘱  | 医嘱    | 容易与临床医嘱混淆  |
| 报告签发   | 报告发布    | 保存报告  | 保存不等于签发    |
| 报告更正   | 修订报告    | 修改报告  | 容易理解为覆盖原版本 |
| 冰冻送检批次 | 冰冻轮次    | 冰冻病例  | 轮次不等于病例    |
| 让步接收   | 有条件接收   | 正常接收  | 风险等级不同     |
| 作废     | 无效      | 删除    | 作废必须保留记录   |

## 4. 文档命名规则

业务文档标题应描述业务对象或业务活动，例如：

```text
标本接收业务规则
切片状态机
报告版本管理
冰冻送检流程
```

避免使用：

```text
页面一
功能模块二
工作站状态
病例表逻辑
```

除非文档确实只描述页面或数据库。

---

## 5. 代码命名规则

代码命名应使用明确英文业务术语。

推荐：

```text
PathologyRequest
PathologyCase
Specimen
BlockBusinessRecord
PhysicalParaffinBlock
PhysicalSlide
SlideLabel
DigitalSlide
TechnicalOrder
OperationalResponsibilityRecord
DiagnosticAssignment
Report
ReportVersion
FrozenSubmission
QualityEvent
AuditEvent
```

`SpecimenContainer` 和 `ProcessingBatch` 仅在医院启用对应扩展能力时使用，不作为默认核心对象命名。

避免：

```text
Data
Info
Record
MainTable
DetailTable
ItemData
BusinessObject
CommonEntity
```

无法表达业务含义的通用命名不得用于核心领域对象。

---

## 6. API 命名规则

API 路径和字段应基于业务对象命名。

推荐：

```text
/pathology-cases
/specimens
/blocks
/slides
/technical-orders
/reports
/report-versions
/frozen-submissions
```

避免：

```text
/workstation-data
/process-data
/common-save
/update-status
/business-list
```

不得通过通用 `update-status` 接口绕过领域命令。

---

## 7. 数据库命名原则

数据库表名应对应明确业务对象。

推荐：

```text
pathology_case
specimen
block_business_record
physical_slide
slide_label
digital_slide
technical_order
operational_responsibility_record
diagnostic_assignment
report
report_version
audit_event
```

组织盒或处理批次的独立表名只有在相应扩展能力确认后再确定；本阶段不据此锁定数据库结构。

避免：

```text
business_main
business_detail
case_extend
common_relation
object_link
status_data
```

数据库具体命名将在数据库设计阶段确定，本节只约束语义。

---

## 8. 页面用词规则

界面可以使用岗位熟悉的名称，但必须与统一术语建立映射。

例如：

```text
“登记工作站”是页面名称；
“病理登记”是业务活动；
“病理病例”是业务对象。
```

不得因为页面叫“取材工作站”，就在领域模型中创建 `GrossingWorkstation` 作为核心业务实体。

---

## 9. 状态命名规则

状态名称必须满足：

1. 属于明确对象；
2. 表示对象所处业务阶段或有效性；
3. 不使用页面名称；
4. 不使用模糊的“已完成”而缺少对象上下文；
5. 不将多个对象状态拼成一个字段；
6. 不通过自由文本保存核心状态。

正确示例：

```text
标本：已接收
蜡块业务记录：待包埋
玻片：待技术处理
报告版本：已签发
```

错误示例：

```text
病例：已接收已取材待切片
状态：工作站3
处理状态：5
```

具体状态将在状态机阶段设计。

## 10. 术语变更规则

术语变更必须记录：

* 原术语；
* 新术语；
* 变更原因；
* 是否改变业务含义；
* 影响文档；
* 影响代码；
* 影响数据库；
* 影响接口；
* 影响测试；
* 生效版本。

仅修改显示名称、但不改变业务含义时，也应保持内部语义稳定。

---

## 11. 待确认术语管理

所有待确认术语应在 `glossary.md` 中明确标记。

不得因为开发需要而私自将待确认术语改为已确认。

后续业务评审完成后，应：

1. 更新定义；
2. 更新状态；
3. 更新相关文档；
4. 评估已生成代码是否受影响。
