## 1. 项目目标

PIS Next 项目旨在重新设计并开发一套生产级病理信息系统。

系统重点解决以下问题：

1. 病理申请、病例、标本、蜡块、切片、数字切片和报告之间的完整追溯；
2. 多标本、多蜡块、多切片场景下的数据一致性；
3. 返工、补取、作废、撤回、更正等异常流程；
4. 冰冻多轮送检及冰剩转常规流程；
5. 报告不可变版本管理；
6. 标签打印、补打和失效管理；
7. 医院接口的幂等、重试、补偿和对账；
8. 权限、审计、并发和医疗数据安全；
9. 不同医院通过配置实现差异化；
10. 系统部署、备份、恢复和运维能力。

---

## 2. 总体建设原则

项目遵循以下原则：

1. 先业务建模，后数据库设计；
2. 先状态机和异常流程，后页面开发；
3. 先完成核心闭环，后扩展外围模块；
4. 默认采用模块化单体架构；
5. 病例、标本、蜡块、切片、技术医嘱、数字切片和报告分别管理状态；
6. 医疗业务历史不得覆盖或物理删除；
7. 所有关键动作必须审计；
8. 所有外部接口必须具备幂等机制；
9. 每个阶段都必须具备明确的验收条件；
10. 未通过验证的阶段不得直接标记完成。
11. 项目采用净室设计，不将旧系统文档、代码、数据库或页面作为新系统设计输入。

- 取材和蜡块管理；

- 包埋；

- 技术医嘱；
- 数字切片管理；
- 初诊、复诊和审核；
- 报告签发和版本管理；
- 报告补充、更正、撤回和重新签发；
- 术中冰冻；
- 冰剩转常规；

- AI辅助诊断；

- 互联网专家结算；
- 社交讨论；
- 科研数据平台；
- 任意流程设计器；
- 与医院生产环境直接连接；
- 使用真实患者数据进行开发测试。

## 5. 阶段执行规则

每个阶段开始前必须：

1. 阅读 `AGENTS.md`；
2. 阅读本文件；
3. 阅读与阶段相关的既有文档；
4. 检查 Git 状态；
5. 明确当前阶段允许修改的文件；
6. 明确验收标准；
7. 识别前置依赖。

每个阶段完成时必须：

1. 完成规定的产出物；
2. 运行适用于当前阶段的检查或测试；
3. 检查 Git 差异；
4. 确认没有敏感数据；
5. 更新本文件中的阶段状态；
6. 更新 `progress.md`；
7. 创建清晰的 Git 提交；
8. 推送至远程仓库；
9. 汇报剩余风险。

## 6. 项目质量门禁

项目必须设置以下质量门禁：

### QG-01：需求门禁

在需求基线完成前，不得批量开发业务功能。

### QG-02：领域模型门禁

在核心对象关系和业务不变量确认前，不得冻结数据库设计。

### QG-03：状态机门禁

在对象状态机和异常矩阵完成前，不得实现完整业务流程。

### QG-04：架构门禁

在模块边界和事务策略完成前，不得初始化大规模业务代码。

### QG-05：数据库门禁

核心表必须具备明确外键、唯一约束、索引和并发控制策略。

### QG-06：业务闭环门禁

常规病理核心闭环验证通过后，才能扩展外围模块。

### QG-07：报告门禁

报告不可变、版本链、更正和撤回机制通过后，才能进入系统验收。

### QG-08：接口门禁

接口重复、乱序、超时、失败重试和对账场景必须通过。

### QG-09：安全门禁

不得存在明文密钥、真实患者数据或已知高危越权问题。

### QG-10：发布门禁

自动化测试、备份恢复、部署文档和已知限制必须齐全。

## 7. 关键业务验收场景

最终系统至少必须通过：

1. 一个申请单包含多个标本容器；
2. 一个病例包含多个标本；
3. 一个标本产生多个蜡块；
4. 一个蜡块产生多张不同用途切片；
5. 部分蜡块完成、部分蜡块返工；
6. 标本拒收；
7. 标本让步接收；
8. 补取材；
9. 重脱水；
10. 重包埋；
11. 重切；
12. 重染；
13. 标签打印错误后补打；
14. 旧标签失效；
15. 技术医嘱产生明确切片；
16. 多轮冰冻送检；
17. 冰剩转常规；
18. 报告签发；
19. 报告更正；
20. 报告撤回失败后补偿；
21. 两名医生并发编辑；
22. HIS重复推送申请；
23. 收费消息重复；
24. 报告回传超时；
25. 数字切片重扫；
26. 权限越权被拒绝；
27. 数据库备份和恢复；
28. 恢复后仍能完整追溯病例。
