# P09 全病理需求基线设计规则

文档状态：P09已基线化
适用阶段：P09-ALL-MODALITY-REQUIREMENT-BASELINE-FINAL
上游基线：P04、P05、P06、P07、P08正式文档及其确认结论

## 1. 规则总则

### P09-RULE-001：需求必须有真实上游依据

每条需求必须同时能够追溯到真实的正式场景、已确认决策、领域对象、聚合、不变量、流程、步骤、决策点、异常入口、状态机对象或真实 Q 编号。引用只使用仓库中已经存在的编号，不以本文件创建新的上游编号。

### P09-RULE-002：需求必须是原子义务

一条需求只表达一个可判断的产品义务。若一条义务同时涉及多个独立责任、对象或验收结果，必须拆分为多个 `P09-REQ-0001` 形式的需求，并分别建立验收依据。

### P09-RULE-003：需求正文使用强制性语言

正式需求使用“系统必须”“系统应”“系统可以”分别表达 MUST、SHOULD、MAY。不得以无法验收的模糊措辞替代优先级、条件、结果或可测量参数。

### P09-RULE-004：需求结构统一

每条需求必须包含需求编号、名称、需求类型、适用病理类型、优先级、安全等级、角色、对象、聚合、触发条件、前置条件、正式需求正文、业务规则、输入、系统义务、输出或形成事实、状态影响、异常处理方向、权限责任、审计要求、医院配置边界、验收准则、依赖、冲突排除、上游追溯、Q 追溯、后续阶段输入和当前状态。

### P09-RULE-005：需求类型固定

需求类型只能使用以下枚举：业务功能；业务规则落实；数据与追溯；安全与权限；审计与合规；集成与互操作；性能与容量；可用性与连续性；恢复与灾备；可维护性与可观测性；易用性与错误防范；配置与扩展；归档、保留与销毁。

### P09-RULE-006：优先级和安全等级独立

优先级使用 MUST、SHOULD、MAY；安全等级使用 S1、S2、S3、S4。优先级表达交付必要性，安全等级表达患者安全、诊断可信度、材料身份、报告完整性或业务连续性的风险，不得互相替代。

### P09-RULE-007：需求必须可验收

每条需求至少有一个正向验收准则。MUST 需求还必须有一个负向验收准则，明确缺失前置条件、身份不一致、责任不明、历史事实被覆盖或外部结果未经核验时的拒绝、隔离、待复核或记录方向。

### P09-RULE-008：业务规则与实现方案分离

P09只规定业务义务、约束、事实、责任、结果和可观察性。持久化结构、交换字段、交互方案、组件选择、部署拓扑和代码组织留给后续阶段，不能反向改变需求语义。

### P09-RULE-009：对象事实保持独立

患者、就诊上下文、申请、病例、标本、蜡块、玻片、制备物、派生材料、提取物、检测任务、检测运行、质控结果、原始结果、有效结果、医学判读、报告版本、投递和对账事实必须保持各自可追溯性。任何一个对象的状态不能代替另一个对象的事实。

### P09-RULE-010：全病理路径必须分流

组织病理、术中冰冻、妇科细胞病理、非妇科细胞病理、穿刺细胞病理、细胞蜡块、分子病理、外送检测和多模态综合诊断共享共性能力，但材料路径、责任、结果和报告关系必须按实际业务分开。不得要求所有病例经过同一条材料加工链。

### P09-RULE-011：实际材料优先于计划材料

计划编号、计划标签、计划玻片、计划检测与实际材料、实际结果、实际责任必须分别记录。实际玻片可以来源于蜡块、细胞学标本、细胞学制备物或外部材料；没有实际发生的中间制备物不得被需求强制创建。

### P09-RULE-012：业务事实不得无痕回滚

已形成的接收、交接、取材、制备、检测、质控、结果、判读、签发、投递、外部回执和销毁事实不得因下游失败而被删除或覆盖。后续动作必须形成补充、更正、隔离、撤回、重新签发、恢复或新版本事实。

### P09-RULE-013：分子结果必须分层

分子检测任务、检测材料、分装或消耗、提取物、检测运行、批次、质控、设备原始结果、有效检测结果、医学判读和报告版本必须分别表达。外部机构返回的结果必须保持外部来源和核验事实，不能冒充本地执行事实。

### P09-RULE-014：细胞责任必须分离

细胞病理需求必须分离标本和制片充分性、现场快速评价、筛查、复核、阴性质量抽查、最终诊断和报告签发资格。细胞学制备记录与稳定保存或复用的制备物不是同一事实；只有实际需要保存或复用时才形成稳定制备物。

### P09-RULE-015：报告以版本保护

已签发报告不可直接修改或覆盖。补充、更正、撤回、重新签发和综合报告必须形成新版本并保留组成报告、原版本、责任人、时间、原因和关系。综合报告不得覆盖组织、细胞或分子组成报告。

### P09-RULE-016：本地与外部状态分离

本地事实、出站事件、投递记录、外部状态、外部回执和对账结果必须分别记录。投递成功不等于外部业务已接收；外部返回内容必须经过来源、完整性、关联关系和医学责任核验。

### P09-RULE-017：权限、责任和审计不可省略

每条涉及医学判断、签发、撤回、纠错、授权、销毁、恢复或外部回传的需求，必须声明执行角色、责任角色、授权依据、必要的强认证或复核条件，并形成可追溯审计事实。

### P09-RULE-018：医院配置不得改变核心规则

医院可以配置显示、分工、提醒、时间目标、项目启用范围、外部机构目录和非核心阈值。医院配置不得关闭或改写身份、来源、责任、材料历史、报告版本保护、患者安全阻断和审计义务。

### P09-RULE-019：未确认参数不伪造承诺

响应时间、吞吐量、容量、保留期、重试次数、恢复目标、可用性目标和外部投递时限等参数使用 `P09-PARAM-001` 形式登记。未获业务确认的参数只记录为“未确认”，不得写成正式数值；未确认参数不自动阻塞 P09。

### P09-RULE-020：编号和验收编号稳定

正式需求编号使用四位序号 `P09-REQ-0001`。验收准则使用 `P09-REQ-0001-AC-01`，负向验收准则在同一需求下继续顺序编号并标记“负向”。参数编号使用 `P09-PARAM-001`。编号一经进入目录，后续阶段只能引用，不得重排或复用。

### P09-RULE-021：双向追溯完整

需求必须能够向上追溯到场景、决策、对象、聚合、不变量、流程、异常、状态机和 Q，也必须能够向下说明对 P10、P11、P12、P14、P24、P25 及必要时 P27 的输入。追溯缺口必须在关闭审查中明确，不得以概括性文字掩盖。

### P09-RULE-022：全病理覆盖完整

需求基线必须覆盖申请、病例、标本、材料、制备、检测、结果、诊断、报告、投递、质量、授权、归档和恢复的完整链路，并覆盖九类病理业务：常规组织病理、术中冰冻、妇科细胞病理、非妇科细胞病理、穿刺细胞病理、细胞蜡块、分子病理、外送检测和多模态综合诊断。

### P09-RULE-023：需求数量由覆盖结果决定

P09不预设需求总数，不以数量目标替代业务覆盖、原子性或验收完整性。正式目录中的107项是本次完成原子拆分、全量追溯和验收核对后的实际结果；后续阶段只能基于新确认的业务事实按变更规则新增或修订，不得为凑数拆分或合并需求。

## 2. P09边界

P09的交付物是可追溯、可验收、可分级、可进入后续设计阶段的产品需求基线。P09不提前定义持久化结构、接口协议细节、交互控件排列、代码、部署、测试实现或完整状态机；这些内容只作为下游输入，不在本阶段展开。

所有需求当前状态统一为 `P09已基线化`。关闭审查结论只有“通过”“有条件通过”“不通过”三种；所有门禁满足时才可使用“通过”。
